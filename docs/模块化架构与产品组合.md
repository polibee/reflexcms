# ReflexCMS 模块化架构与产品组合设计

> 回答三个问题：**forum 与 CMS 的评论边界？每个模块能否单独抽出部署？如何用同一套代码孵化多个产品（如网盘）？**
> 上游：`docs/工程化开发计划.md`（ADR 索引）、`docs/扩展性架构设计.md`（三层扩展模型）。本文结论登记为 ADR-011/012。

---

## 1. 结论先行

1. **评论边界**：Forum 用 `replies`（楼层制、实时生效、随帖生命周期），CMS 用 `comments`（审核制 pending→approved/rejected、挂文章）。两者表结构、状态机、权限前缀完全独立，**不存在也不允许共享"评论"实现**；唯一共享的是多态 `likes` 点赞表（按 `likeable_type` 天然隔离数据）。
2. **单模块可抽取**：是。代码层以 `kernel.Module` 接口 + 产品组合层（`products/` + `cmd/` 多入口）保证「一个模块 = 一个目录 = 一份迁移 = 一组路由/资源」，抽走目录并保留组合声明即可独立成产品。
3. **多产品孵化**：新增产品 = 新增一个 modules 包 + 一个 cmd 入口 + （可选）admin 前端模块目录。网盘程序即未来某个 `modules/drive`。

---

## 2. 分层与依赖规则

```
┌─────────────────────────────────────────────┐
│ products/  +  cmd/<product>/main.go         │  组合层：决定启用哪些模块
│ （Full / Blog / Forum / 未来 Drive…）        │  允许 import 任何模块做接线
├─────────────────────────────────────────────┤
│ feature modules:  cms │ forum │ comment │   │  功能模块：互相不可见
│ notification │ settings │ (drive…)          │
├─────────────────────────────────────────────┤
│ platform core:                              │  平台内核：所有产品必备
│  adminhub(网关) · auth(会话) · access(RBAC)  │
├─────────────────────────────────────────────┤
│ kernel 接口 + app/support/* 工具             │  内核契约，向内依赖
└─────────────────────────────────────────────┘
```

**铁律**：
- feature module 之间**禁止相互 import**；跨模块协作只能：(a) 通过组合层接线事件；(b) 共享逻辑下沉到 `app/support/*`；
- feature module → platform core 单向依赖（注册 Spec、复用 CheckPermission 等）；
- 所有模块面向 `kernel.Module` 接口实现，不感知彼此存在。

## 3. kernel.Module 契约

```go
type Module interface {
    Name() string                                   // "cms"
    Migrations() []schema.Migration                 // 该模块自己的全部迁移
    Routes()                                        // 注册路由（WithRouting 阶段调用）
    Boot()                                          // 注册 Spec/Seeder/事件/调度（Boot 阶段调用）
}
```

平台核心同样实现该接口（access/auth 也是模块，只是"必选"）；`adminhub.RegisterCoreRoutes()`（通用网关+stats）由 bootstrap 固定装配，不属于任何 feature module。

**迁移归属**：物理文件仍集中在 `database/migrations/`（便于统一命名排序），但通过分组构造函数声明归属——`AccessMigrations() / AuthMigrations() / CmsMigrations() / ForumMigrations()`；新模块直接在 `database/migrations/<module>.go` 里加同名分组函数。

## 4. 产品组合

```go
// products/products.go —— 组合层唯一允许"认识所有人"的地方
func Full() []kernel.Module  { return []kernel.Module{access.New(), auth.New(), cms.New(), forum.New(), settings.New(), comment.New(notification.New()), ...} }
func Blog() []kernel.Module  { return []kernel.Module{access.New(), auth.New(), cms.New()} }
func Forum() []kernel.Module { return []kernel.Module{access.New(), auth.New(), forum.New()} }
```

入口：

| 入口 | 启用 | 用途 |
|---|---|---|
| 根 `main.go` | Full | 默认产品（本仓库主形态） |
| `cmd/blog/main.go` | access+auth+cms | 纯博客产品 |
| `cmd/forum/main.go` | access+auth+forum | 纯论坛产品 |

启动方式：`go run .`（Full）/ `go run ./cmd/blog`；迁移同理 `go run ./cmd/blog artisan migrate` 只会建 CMS 相关表。

**跨模块事件接线在组合层完成**：例如 Full 产品把 `comment` 模块的 `CommentModerated` 事件接到 `notification` 的写入服务；Blog 产品不装 forum，自然没有回复通知。模块自身只派发事件、暴露服务，不知道谁在听。

## 5. 单模块抽取与部署流程（SOP）

以「只把 CMS 部署成独立博客」为例：

1. **后端**：复制仓库 → 删除 `modules/forum*`、`cmd/forum` → `products.Blog()` 已是默认组合 → `go build ./cmd/blog`。无需改任何 cms 内部代码。
2. **数据库**：全新库执行 `./cmd/blog artisan migrate && db:seed`，只会生成平台表 + CMS 表。
3. **前端（admin）**：复制 `admin/` 整体 → 删除 `app/modules/{forums,topics,replies}` → 在 `plugins/admin.ts` 移除对应注册行 → 清空 `server/utils/resourceConfigs.ts` 中多余条目。
4. **验证**：跑 `node scripts/contract-test.mjs <地址>`（脚本按产品裁剪断言段落即可）。

反向操作（把模块并入现有产品）：拷入模块目录 + 组合层加一行 + resourceConfigs 加一段。

## 6. 新产品配方（示例：网盘 drive）

1. `backend/modules/drive/`：models(files,folders) / services(配额,分享) / http(上传,下载动作) / events(FileShared) / register.go——实现 `kernel.Module`；
   出站请求（拉取远端文件等）必须经 `support/safefetch`；存储优先 `facades.Storage()`（S3 兼容盘可直接换 driver）。
2. `database/migrations/drive.go`：分组构造函数 `DriveMigrations()`。
3. `products.Drive()` + `cmd/drive/main.go`。
4. admin 前端：`admin/app/modules/drive/` 资源声明 + 组合根一行。
5. 公共前台（若需要）：Nuxt Layer 主题消费 `/api/v1/**` 新增段。

## 7. forum.replies vs cms.comments 职责对照

| 维度 | forum/replies | cms/comments |
|---|---|---|
| 宿主 | topics（楼层制） | articles |
| 生效策略 | 即时可见 | pending 审核→approved 才可见 |
| 结构 | floor 序号 + parent_id 楼中楼 | parent_id 楼中楼 |
| 计数 | topic.reply_count（事务内维护） | article.comment_count（仅 approved 计入，重算自愈） |
| 权限前缀 | replies.* | comments.*（moderate 动作独立） |
| 通知触发 | ReplyCreated → 通知楼主 | CommentModerated → 通知评论者 |
