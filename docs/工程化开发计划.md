# ReflexCMS 工程化开发计划

> 基于《开发文档.md》（Goravel + Nuxt CMS+BBS 设计蓝本）优化而来。
> 本版关键调整：**砍掉公共前台、引入 polibee/nuxtadmin 作为唯一前端形态、以模块化里程碑推进**。
> 配套文档：`docs/开发文档.md`（原始蓝本）、`docs/nuxtadmin/docs/开发指南.md`（后台框架指南）、`docs/nuxtadmin/docs/工程审计报告.md`（后台生产化缺口清单）。

---

## 0. 结论摘要

1. **范围重划**：MVP 只交付两件事——Goravel 后端 API + nuxtadmin 管理后台。公共用户界面（Nuxt SSR 前台）整体延后到 Phase B，但后端按「公共读接口」预留版本化命名空间。
2. **集成模式**：nuxtadmin 保留其 Nitro 服务端作为 **BFF 薄代理层**，把内存仓储替换为「原样转发到 Goravel」的 HTTP 客户端。nuxtadmin 框架代码零改动，同时恰好补齐其审计报告列出的两个 P1 生产化缺口（真实数据库、真实鉴权）。
3. **核心工作量在 Goravel 侧**：实现一套**注册表驱动的通用管理资源网关**，与 nuxtadmin 现有契约逐字对齐（路径、查询参数、分页信封、错误码、权限命名）。
4. **六个里程碑 M0–M5（约 6 周）**，每个里程碑有明确的任务分解、交付物与验收标准（DoD），可独立验收、可中断续接。
5. **站点模式**：内置 blog / forum / hybrid 三种运行时模式（存 settings，后台随时切换，零迁移）；前台延后至 Phase B，但公共 API 契约随 M2–M4 冻结。

## 1. 相对原开发文档的优化决策

| # | 原方案 | 优化后 | 理由 |
|---|---|---|---|
| O1 | Nuxt 同时承担公共前台 + 后台 | 公共前台移出 MVP；后台直接采用 nuxtadmin | 控制首阶段范围；nuxtadmin 是声明式资源框架（Filament 思想），CRUD 页面自动生成，开发效率远高于手写后台 |
| O2 | 后端为每个资源手写 Controller | 注册表驱动的通用资源网关 + 专用动作路由兜底 | 与 nuxtadmin 的 `[resource]` 动态路由天然匹配；新增资源只需注册 Spec，不写样板代码 |
| O3 | `categories` 一张表被 CMS 和 BBS 复用 | 拆分为 `article_categories` 和 `forum_categories` | 两套分类的生命周期、字段、排序逻辑不同；复用一张表是原文档的隐性坑 |
| O4 | `users.role` 单字符串字段 | `roles` 表 + `permissions` JSONB 数组，数据驱动 RBAC | 支撑权限双层执行（前端过滤 UI + 后端强制校验）；角色可运营期调整而无需发版 |
| O5 | 未定义后台会话机制 | 不透明 Token（opaque token）哈希落库 + httpOnly Cookie，弃用 JWT | 可即时吊销（封禁管理员立即生效）；BFF 透传零状态 |
| O6 | 列表浏览量/回复数直接 COUNT | 冗余计数列（事务内维护）+ 浏览量走 Redis 缓冲定时落库 | 高频读场景避免全表聚合；列表页排序依赖这些计数 |
| O7 | 搜索直接上 Meilisearch | MVP 用 PostgreSQL 全文检索（tsvector + GIN），Meilisearch 延后 | 少一个常驻服务；PG 方案对 MVP 数据量足够，且 Search 以接口隔离便于日后替换 |
| O8 | AI 功能无落地形态 | `modules/ai` 仅保留接口与事件占位：文章发布事件 → 队列 Job 接口 → 结果回写字段 | 架构上预留管道但不接真实模型，避免过早复杂度 |
| O9 | 未考虑服务端外呼安全 | 建立统一 `support/safefetch` 出站工具：仅允许 http/https，请求前校验 host，拒绝 localhost、环回、私有及保留地址，DNS 解析后二次校验 | 封面图抓取、未来 Webhook/AI 外呼全部走此工具，杜绝 SSRF 注入面 |
| O10 | 未区分站点形态（原稿默认博客+论坛全量并存） | 引入 `site.mode` 运行时配置：`blog \| forum \| hybrid`，控制公共内容的暴露范围 | 支撑同一套代码服务三种产品形态；先启单一模式、后续经后台开启其他模式，零迁移零发版 |

## 2. 总体架构

```
浏览器
   │
   ▼
nuxtadmin（Nuxt 4 · Nitro）           ← admin/ 目录，自维护 fork
   ├─ app/modules/**                  ← 业务模块（资源声明，页面自动生成）
   └─ server/utils/{db,auth}.ts       ← BFF：转发 Goravel（本次唯一改造点）
        │  Authorization: Bearer <token>（从 admin_session Cookie 透传）
        ▼
Goravel v1.18 API（Go ≥ 1.23）
   ├─ /api/auth/*                     ← 登录/会话/注销
   ├─ /api/admin/:resource/*          ← 通用管理资源网关（注册表驱动）
   ├─ /api/admin/stats                ← 仪表盘聚合
   └─ /api/v1/**                      ← 公共读接口（Phase B 启用，现在预留）
   │
   ├─ modules: auth · access · cms · forum · comment · notification · settings · search · ai
   ▼
PostgreSQL 16（数据 + 全文检索）      Redis 7（缓存/计数缓冲/队列驱动）
```

### 2.1 关键集成决策

**D1 · BFF 代理而非直连**
nuxtadmin 的表格引擎 `$fetch('/api/admin/...')` 依赖同源 Cookie 自动携带；直连 Goravel 需要 CORS + 跨域 Cookie（SameSite=None）改造，侵入框架层。选 BFF：Nitro 处理器保持不动，仅把 `server/utils/db.ts` 的五个仓储函数（`getCollection/insertRow/findRow/updateRow/deleteRows/applyQuery`）替换为对 Goravel 的同路径转发。**转发是路径保真的**——方法、路径、Query、Body 原样透传，非 2xx 状态码原样返回（401/403/404/422 语义由 Goravel 保证），因此前端通知管线无需任何修改。

**D2 · Goravel 直接复刻 nuxtadmin 路径**
Goravel 实现与 nuxtadmin 现有服务端完全相同的路径（`/api/auth/login` 等），使代理层退化为纯管道。公共前台未来的接口走独立的 `/api/v1/**` 命名空间，互不干扰。

**D3 · 双侧权限声明 + 契约测试锁定**
资源元数据（searchable 字段、权限前缀）在前端 `resourceConfigs.ts` 与后端 ResourceSpec 各声明一份，用自动化契约测试比对两侧一致性，防止漂移。不为省这一份声明去改框架加「schema 下发」机制。

## 5. 冻结的接口契约

以下契约为前后端的共同宪法，变更需走 ADR 并同步更新契约测试。

### 5.1 认证

| 方法 & 路径 | 说明 | 权限 |
|---|---|---|
| `POST /api/auth/login` | `{email,password}` → 设置 `admin_session` Cookie | 公开（有限流） |
| `GET /api/auth/me` | 当前用户 `AuthUser` | 登录 |
| `POST /api/auth/logout` | 吊销会话 | 登录 |

```ts
interface AuthUser {
  id: number
  name: string
  email: string
  role: string              // 角色标识（数据驱动，前端类型放宽为 string）
  permissions: string[]     // 如 ['*'] 或 ['articles.view','articles.edit']
}
```

会话机制：登录成功后 Goravel 生成随机 token（≥32 字节），SHA-256 哈希后存 `admin_sessions` 表（含过期时间、IP、UA），明文 token 仅在响应中出现一次。Cookie 为 `httpOnly + SameSite=Lax`，生产环境追加 `Secure`。封禁用户/删除会话即刻失效。

### 5.2 通用管理资源网关

| 方法 & 路径 | 说明 | 权限 |
|---|---|---|
| `GET /api/admin/:resource` | 列表：`q,page,perPage(≤200),sortBy,sortDir` → 分页信封 | `{prefix}.view` |
| `POST /api/admin/:resource` | 创建（按 Spec 校验） | `{prefix}.create` |
| `GET /api/admin/:resource/:id` | 详情 | `{prefix}.view` |
| `PUT /api/admin/:resource/:id` | 更新（仅接受已知字段） | `{prefix}.edit` |
| `DELETE /api/admin/:resource/:id` | 删除 | `{prefix}.delete` |
| `POST /api/admin/:resource/bulk-delete` | `{ids:number[]}` → `{removed:number}` | `{prefix}.delete` |
| `POST /api/admin/:resource/:id/{action}` | 专用动作（publish/pin/close…，按需注册） | 按 Spec 定义 |

分页信封（与 `shared/types/api.ts` 的 `Paginated<T>` 逐字段一致）：

```json
{ "items": [], "total": 100, "page": 1, "perPage": 10, "totalPages": 10 }
```

错误语义：401 未登录、403 无权限（`Missing permission: xxx.yyy`）、404 资源不存在、422 参数校验失败。成功直接返回数据本体，无额外包裹。

**安全红线（Go 侧强制）**：
- `sortBy` 必须命中 Spec 白名单，否则回退 `id`——杜绝 SQL 注入；
- `q` 搜索仅作用于 `Searchable` 白名单字段；
- 输出经 `Transform` 裁剪，密码哈希等敏感字段永不出网。

### 5.3 仪表盘

`GET /api/admin/stats` 返回聚合计数与序列。MVP 形态：

```json
{
  "usersTotal": 0, "usersActive": 0,
  "articlesTotal": 0, "articlesPublished": 0,
  "topicsTotal": 0, "topicsToday": 0,
  "pendingComments": 0,
  "recentArticles": [], "publishSeries": [{ "label": "W-9", "count": 0 }]
}
```

配套替换演示 Widget（orders/营收图）为 CMS/Forum Widget。

### 5.4 公共接口预留（/api/v1，Phase B 全面启用）

| 方法 & 路径 | 说明 |
|---|---|
| `GET /api/v1/site/config` | 站点配置 `{ name, mode, seo{} }`——前台启动时的首个调用，驱动导航与路由形态（M4 交付最小实现作为验收口） |

**站点模式门控语义**：`site.mode ∈ {blog, forum, hybrid}`。单一模式下，被禁用板块的公共读接口一律返回 404（对用户与搜索引擎均语义正确）；hybrid 全开。门控由 settings 服务统一判定并挂在 `/api/v1` 中间件层，**禁止**在各控制器里散落判断。管理后台不受模式影响——所有内容模块始终可治理，模式只决定前台可见性。

## 6. 数据库设计（优化版）

约定：主键一律 `id BIGSERIAL`；内容表带 `created_at/updated_at/deleted_at`（软删除）；时间戳 `TIMESTAMPTZ`；枚举用字符串列 + 应用层常量（避免 PG ENUM 迁移负担）。

### access 模块

**roles** — `id, name(unique), display_name, permissions JSONB(text[]), sort, timestamps`
预置角色：`super-admin(* )`、`editor`(内容增删改查)、`moderator`(评论/帖子治理)、`viewer`(全局只读)。

**users** — `id, username(unique), email(unique), password(bcrypt), avatar, bio, website, role_id FK, status(active|inactive|banned), banned_at, last_login_at, timestamps`
索引：username/email 唯一索引；`(status)`。

**admin_sessions** — `id, user_id FK, token_hash(unique), expires_at, ip, user_agent, last_used_at, created_at`
索引：`token_hash` 唯一；`(user_id)`；定期清理过期行（Scheduler）。

### cms 模块

**article_categories** — `id, name, slug(unique), description, sort, timestamps`

**tags** — `id, name, slug(unique), timestamps`

**articles** — `id, author_id FK, category_id FK, title, slug(unique), content(TEXT, Markdown 原文), summary, cover, status(draft|published|archived), published_at, view_count, comment_count, ai_summary, ai_keywords(JSONB), search(TSVECTOR 生成列), timestamps, deleted_at`
索引：`slug` 唯一；`(status, published_at DESC)`；`GIN(search)`；`(author_id)`。

**article_tags** — `article_id, tag_id`，复合主键。

### forum 模块

**forum_categories** — `id, name, slug(unique), description, icon, sort, topic_count, timestamps`

**topics** — `id, user_id FK, forum_category_id FK, title, content, status(open|closed), is_pinned BOOL, is_featured BOOL, reply_count, like_count, view_count, last_reply_at, last_reply_user_id, timestamps, deleted_at`
索引：`(forum_category_id, is_pinned DESC, last_reply_at DESC)`（板块首页主查询）；`(status)`。

**replies** — `id, topic_id FK, user_id FK, parent_id NULL, content, like_count, floor INT, timestamps, deleted_at`
索引：`(topic_id, floor)`。

**likes** — `id, user_id FK, likeable_type VARCHAR, likeable_id BIGINT, timestamps`，唯一约束 `(user_id, likeable_type, likeable_id)`。

### comment 模块

**comments** — `id, article_id FK, user_id FK, parent_id NULL, content, status(pending|approved|rejected|spam), timestamps, deleted_at`
索引：`(article_id, status)`；`(status)` 供审核队列。

### 其他

**notifications** — `id, user_id FK, type, data JSONB, read_at, timestamps`；索引 `(user_id, read_at)`。
**settings** — `key(PK), value(JSONB), group, updated_at`。预置键：`site.mode`(blog|forum|hybrid，默认 hybrid)、`site.name`、`site.seo.description`、`site.icp`。
**admin_operation_logs**（M5）— `id, user_id, action, resource, resource_id, payload_snapshot JSONB, ip, user_agent, created_at`。

**计数一致性规则**：`reply_count/comment_count/topic_count` 一律在写库事务内随业务行同增减；`view_count` 例外走 Redis `INCR`，Scheduler 每 5 分钟批量落库（允许秒级误差换取写性能）。

## 7. 后端模块设计与依赖规则

### 7.1 模块内标准结构

```
modules/cms/
├── models/          # Article, Category, Tag（GORM 标注）
├── repositories/    # 数据访问，仅本模块可见
├── services/        # 业务逻辑（状态机、slug 生成、计数维护）
├── http/            # 专用动作控制器（publish 等）
├── events/          # ArticlePublished …
└── jobs/            # 异步任务（AI 摘要占位、计数落库）
```

### 7.2 依赖铁律

1. 模块间**禁止直接引用对方 repository/model 内部**，只能依赖对方 Service 导出的接口或通过事件总线通信；
2. `adminhub`（通用网关）位于最底层，被各内容模块单向注册 Spec，反向禁止；
3. 所有出站 HTTP 必须经 `support/safefetch`，任何绕过直接使用 http.Client 的代码不予合入。

### 7.3 ResourceSpec（网关注册表）

```go
type ResourceSpec struct {
    Name             string                              // URL 段，如 "articles"
    Model            any                                 // GORM 模型
    Searchable       []string                            // q 搜索白名单
    Sortable         []string                            // sortBy 白名单，默认 [id, created_at]
    PermissionPrefix string                              // 默认 = Name
    Filters          map[string]FilterFunc               // 可选固定筛选项
    ValidateCreate   func(req map[string]any) error      // 422 校验
    ValidateUpdate   func(id uint64, req map[string]any) error
    Transform        func(m any) map[string]any          // 输出裁剪
    Overrides        map[string]HandlerFunc              // 可选：覆写某动词
}
```

通用路由在启动时一次性注册全部 Spec；需要特殊流程的资源（如文章发布、帖子置顶）走第 7.1 节的专用动作路由，网关不做业务特判。

## 9. 里程碑计划（M0–M5）

> 每个 DoD 即合并门槛；任一里程碑可独立验收，中断后续接不影响整体结构。

### M0 · 工程奠基（≈3 天）

**目标**：一键起全栈，双流水线绿。

- [ ] Monorepo 整备：`docs/nuxtadmin` → `admin/`，四道闸门（lint/typecheck/test/build）恢复全绿
- [ ] `backend/` 初始化：Goravel v1.18 + gin + gorm(postgres)，连接 Compose 内 PG/Redis，`go run .` 可访问健康检查
- [ ] `deploy/docker-compose.yml`（pg16 + redis7）、根 Makefile（dev/test/lint/migrate/seed）
- [ ] CI 双流水线：backend（golangci-lint + go test + build）、admin（沿用现有四道闸门）
- [ ] `.env.example` 与配置加载验证；Git 分支规范与 PR 模板落档

**DoD**：`make dev` 拉起数据库与两个服务；两条 CI 流水线在样例 PR 上全绿。

### M1 · 平台底座：认证 + RBAC + 通用网关（≈1 周）★ 最关键

**目标**：后台能登录、能管用户与角色，通用资源网关跑通任意注册资源。

- [ ] 迁移 + Seeder：`roles/users/admin_sessions`，预置四角色与初始超管账号
- [ ] `modules/auth`：登录（bcrypt 校验 + 登录限流 5 次/分/IP）、opaque token 签发/校验/吊销、me/logout
- [ ] `modules/access`：权限匹配器（`*` / `prefix.*` / 精确，与前端 `can()` 同语义）+ 单测
- [ ] `modules/adminhub`：ResourceSpec 注册表、通用五件套 + bulk-delete 路由、分页信封、sortBy/Searchable 白名单、Transform 裁剪、401/403/404/422 错误语义
- [ ] `/api/admin/stats` 基础版
- [ ] admin 侧：完成第 8 节 db.ts/auth.ts/types 三处改造；接入 `users`、`roles` 两个真实资源模块；移除 posts/orders 演示模块
- [ ] 契约测试脚本 `scripts/contract-test.mjs`：对每个已注册资源跑「列表形状 → 创建 → 详情 → 更新 → 批量删除」往返断言
- [ ] 权限矩阵集成测试：admin 全通过 / editor 越权 403 / viewer 写操作 403（对应审计报告实测项）

**DoD**：浏览器中以后台真实账号完成登录 → 用户 CRUD → 角色分配 → 越权被拒；契约测试与权限矩阵测试进 CI 且绿；`npm test` 中 applyQuery 相关旧用例退役、同等语义断言迁移至 Go 侧。

### M2 · CMS 模块（≈1 周）

**目标**：文章生命周期在后台完整闭环。

- [ ] 迁移 + Spec：`article_categories/tags/articles/article_tags`
- [ ] Service：slug 唯一生成（冲突追加短随机串）、状态机（draft→published→archived，发布写 `published_at` 并派发 `ArticlePublished` 事件）
- [ ] 专用动作：`POST /api/admin/articles/:id/publish|unpublish`（带确认弹窗的 Action）
- [ ] PG 全文检索：tsvector 生成列 + 触发器/应用层刷新；列表 `q` 走 GIN 检索（中文按词元降级处理，Meilisearch 兜底记入风险）
- [ ] 封面上传：本地 storage 起步（S3 兼容接口预留）；上传校验 MIME 白名单 + 大小上限；外链封面 URL 经 `support/safefetch` 校验
- [ ] `modules/ai` 占位：订阅 `ArticlePublished` → 空 Job 接口（写注释预留 ai_summary 回写）
- [ ] admin 侧：articles/categories/tags 三个资源模块 + 仪表盘 Widget（统计卡 + 最近文章 + 发布趋势图消费 `stats.publishSeries`）

**DoD**：后台完成「建分类打标签 → 写草稿 → 发布 → 搜索命中 → 下架归档」全流程；发布事件可在日志中观测到 Job 触发；service 层关键逻辑（slug 冲突、状态机非法流转）有单测。

### M3 · Forum 模块（≈1 周）

**目标**：板块/帖子/回复/点赞可用，计数准确。

- [ ] 迁移 + Spec：`forum_categories/topics/replies/likes`
- [ ] Service：回复事务（插 reply 行 + `reply_count++` + `last_reply_*` 同事务更新）、楼层号分配、点赞幂等（唯一约束 + 冲突忽略）
- [ ] 浏览量：详情接口 Redis `INCR` + Scheduler 定时落库；列表排序支持按热度（加权 view/reply/like，具体权重实现于 Service，可配）
- [ ] 专用动作：置顶/取消置顶、加精、关闭/开放（均挂权限 `topics.pin` 等）
- [ ] admin 侧：forums/topics/replies 资源模块（topics 列表含板块筛选 badge、置顶标记列）；仪表盘补充论坛统计 Widget

**DoD**：后台完成建板块 → 发帖 → 回复 → 点赞 → 置顶全流程；并发回复压测下 `reply_count` 与实际行数一致（事务保证有集成测试锁定）。

### M4 · 社区能力：评论审核 + 通知 + 设置（≈1 周）

**目标**：内容治理闭环与站点可配置。

- [ ] `comment` 模块：迁移 + Spec + 审核队列（pending 过滤视图）、批量通过与拒绝 Action（`comments.moderate`）
- [ ] `notification` 模块：事件监听（回复/审核结果/点赞）→ 队列异步写入 notifications；后台提供通知列表只读视图与「全部已读」Action
- [ ] `settings` 模块：KV 存储 + 类型化读取接口（网站名称/SEO 描述/备案号/每页条数默认值）；admin 资源模块以表单形式呈现
- [ ] 站点模式 `site.mode`（blog|forum|hybrid，Seeder 默认 hybrid）：设置表单提供带说明的下拉项，保存后立即失效 Redis 缓存；后台导航始终展示全部内容模块（内容治理与前台可见性解耦）
- [ ] 用户维度聚合接口预留：`GET /api/v1/users/:id/overview`（文章数/帖子数/评论数），供未来公共前台与用户主页直接复用

**DoD**：「用户回复文章评论 → 编辑收到通知 → 审核驳回 → 作者收到结果通知」链路贯通（队列异步、失败重试可观测）；设置项修改后在 stats 与列表行为中生效；切换站点模式后 `/api/v1/site/config` 即时返回新值（验证缓存失效链路）。

### M5 · 加固与上线准备（≈1 周）

**目标**：生产前置清单清零。

- [ ] 安全：登录防爆破加固（指数退避 + 账号级锁定）；全局速率限制中间件；Cookie `Secure`；CORS 白名单（为 Phase B 前台预留）；上传文件名清洗与存储隔离
- [ ] `support/safefetch` 全面接管出站请求：仅 http/https；请求前 host 校验，拒绝 localhost、环回、私有（10/8、172.16/12、192.168/16）、链路本地（169.254/16）与保留地址；DNS 解析后对目标 IP 二次校验；附单测覆盖各类绕过尝试
- [ ] 审计日志：`admin_operation_logs` 落地，网关与专用动作统一埋点；后台只读查看页
- [ ] 可观测性：结构化日志规范、慢查询日志阈值、`/healthz`（DB/Redis 探活）
- [ ] 性能基线：核心列表接口 P95 < 200ms（种子数据 ≥ 1 万行文章/10 万行回复）；缺失索引补齐
- [ ] 运维：`deploy/backup.sh`（pg_dump + 保留策略）与恢复演练记录；生产部署文档（TLS、环境变量清单、进程守护）
- [ ] E2E 冒烟：Playwright 走通「登录 → 发文 → 发布 → 审核评论 → 置顶帖」关键路径

**DoD**：审计报告第五节三项 P1 全部关闭；E2E 绿；备份恢复演练通过；性能基线达标并存档数据。

### 前台启动策略与 Phase B（MVP 之后，另行立项）

**顺序结论：前台不在 MVP 开发，但其 API 契约随域模型同步冻结。**

- **M2–M4**：各模块定稿 Service 的同时，顺手固化 `/api/v1` 公共契约草案（文章/帖子列表与详情、首页聚合、搜索、站点配置），沉淀到 `docs/api-v1.md`——避免 Phase B 从代码反推接口；
- **Phase B 第一步·前台设计冲刺（≈1 周）**：基于冻结契约完成信息架构——按三种站点模式分别产出首页与导航形态、页面清单、视觉稿——评审后再进入编码；
- **实现要点**：Nuxt SSR + SEO（meta/canonical/OG）、sitemap 按 `site.mode` 生成、模式感知路由（单一模式下被禁用板块的路由不注册或返回 404）、登录注册/OAuth 对接；
- **其余特性**：收藏/关注/私信/积分、Meilisearch 接入（替换 search 适配器实现即可）、AI 摘要/审核/搜索真实模型接入。

## 10. 工程化规范

### 10.1 Git 与协作

- 分支：`main` 受保护，功能走 `feat/<module>-<topic>` 短分支，PR 合并制；
- Commit：`feat|fix|refactor|docs|test|chore(scope): summary`（与 nuxtadmin 现行建议一致）；
- PR 必须过对应 CI 流水线；跨栈改动（契约变更）需两个流水线都绿并更新本文档第 5 节。

### 10.2 质量闸门

| 侧 | 闸门 | 标准 |
|---|---|---|
| backend | golangci-lint / go test ./... / go build | 0 error；核心 service/权限匹配器/网关白名单必须有单测 |
| backend | 集成测试 | 网关 CRUD 往返 + 权限矩阵 + 计数一致性，跑在 CI 的 PG 服务容器上 |
| admin | lint / typecheck / test / build | 维持既有 0 基线 |
| 跨栈 | 契约测试 | 每次契约相关 PR 必跑；两侧资源元数据比对一致 |

### 10.3 安全基线

- 密码 bcrypt（cost ≥ 12，走 Goravel Hashing facade）；
- 所有排序/搜索字段白名单化（见 5.2 红线）；
- 出站请求一律 `support/safefetch`（SSRF 防护规范见 O9 与 M5）；
- 上传：扩展名 + MIME 双校验、大小上限、随机文件名、独立存储目录不可执行；
- 日志脱敏：密码/token 永不入日志；
- 依赖：Go 模块与 npm 依赖纳入 Dependabot/renovate 类自动升级提醒。

### 10.4 通用 DoD（所有任务适用)

1. 功能在真实浏览器中人工验收通过；
2. 新增逻辑有测试且 CI 绿；
3. 若涉及契约/数据库/配置变更，已同步本文档与 `.env.example`；
4. 无遗留 TODO 混入主干（用 issue 承接）。

## 11. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| nuxtadmin 为个人项目，上游演进不确定 | 框架层修复需自行承担 | 已定为自维护 fork（vendor 进仓库）；框架层冻结不改的原则降低跟涨成本 |
| PG 中文全文检索效果弱 | 搜索体验打折 | MVP 明示按词元降级；Search 以接口隔离，Phase B 换 Meilisearch 只动 adapter |
| 通用网关抽象过度或不足 | 特殊需求被迫改框架层 | Spec 提供 Overrides 逃生舱 + 专用动作路由分流；一旦发现要改框架层即触发架构复审 |
| 契约双侧声明漂移 | 前端表单能提交但后端 422 | 契约测试进 CI 强制比对（D3） |
| 浏览量/计数最终一致性与展示误差 | 数据轻微偏差 | 仅 view_count 走缓冲且明确容忍秒级误差；其余计数强事务 |
| 新增公共接口遗漏模式门控 | 单一模式下泄露禁用内容 | 门控统一挂在 /api/v1 中间件（见 5.4），不依赖各控制器自觉 |
