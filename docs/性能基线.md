# 性能基线（M5 存档）

> 实测环境：本机 Windows（Laragon PG 17.5 @5433 + Redis 5.0）+ Go 后端单实例。
> 数据规模：`scripts/perf-seed.sql` —— 文章 **10,023** 行、帖子 **2,008** 行、回复 **100,080** 行。
> 工具：`scripts/perf-test.mjs`（每端点预热 3 次后采样，默认 40 次；`PERF_N` 可调）。
> 首次存档：2026-08-25。

## 实测结果（40 样本）

| 端点 | 数据量 | p50 | p95 | max | 备注 |
|---|---|---|---|---|---|
| GET /api/admin/articles（按发布时间排序） | 10k 行 | 14.5ms | **16.3ms** | 16.9ms | 走 (status,published_at) 组合思路索引 |
| GET articles?q=lorem（PG FTS） | 10k 行 | 3.0ms | **3.6ms** | 4.1ms | GIN(search_vector) 命中 |
| GET articles?q=中文（ILIKE 兜底） | 10k 行 | 44.6ms | **53.4ms** | 55.4ms | 顺序扫描，符合预期降级 |
| GET /api/admin/topics?sortBy=hot | 2k 行 | 5.6ms | **6.8ms** | 7.7ms | SortRaw 热度表达式 |
| GET /api/admin/replies | 100k 行 | 12.9ms | **16.3ms** | 16.9ms | topic_id/floor 索引 |
| GET /api/admin/stats（聚合） | 多表 | 153.9ms→**3.7ms**(缓存后) | 162.6ms→**6.2ms** | 172ms | 加 30s TTL 缓存后命中 |

**结论：全部核心列表 P95 < 200ms 达标**（目标值见工程化开发计划 §M5）。最重路径为 CJK ILIKE 兜底（无索引顺序扫描），数据量再上一个数量级时应接入 Meilisearch（Search 接口已隔离，替换 adapter 即可）。

## 已知优化记录

1. `stats` 原始实现每次全表 COUNT×8，10 万回复下 ~160ms——已加 **30 秒 TTL 聚合缓存**（Redis 字符串往返），命中率 100%（仪表盘刷新间隔内）。缓存失效：TTL 自然过期。
2. Redis 缓存回读值为字符串类型，stats 控制器做了 string/map 双分支解码——新增缓存读取时注意同样处理。

## 复测方法

```bash
psql ... -f scripts/perf-seed.sql     # 幂等种子
node scripts/perf-test.mjs            # 输出各端点 p50/p95/max，非零退出码 = 超标
```
