# ReflexCMS 扩展性架构设计

> 回答三个问题：**要不要提前做插件系统？模块化边界怎么划？主题（前后端功能分离）怎么设计？**
> 上游文档：`docs/工程化开发计划.md`（总计划与 ADR 索引）。本文档的结论已同步为该计划 ADR-009/010。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 插件系统要不要现在开发？ | **不开发运行时插件系统。** 用「模块化 + 三层扩展点」替代；触发条件出现后再升级为 L3 插件架构（见 §5） |
| 模块化做了吗？ | 已内建：后端 `modules/*` 域模块 + 注册表扩展点；后台 nuxtadmin 的 `defineModule/defineResource` 本身就是声明式插件机制 |
| 后端功能后端做、前端功能前端做？ | **是，且更彻底——后端无头化。** 后端只输出 API 与事件，不渲染任何前台页面；主题 100% 是前端概念 |

核心判断依据：插件系统的价值在于让**第三方**在不修改主体代码的情况下扩展**别人的**部署。而 ReflexCMS 是自研自营系统，扩展者就是我们自己——对自研系统而言，「新增一个 modules/ 目录」的成本远低于「设计、实现、维护一套插件 ABI」。过早做插件系统的真实代价是：把还不稳定的内部接口冻结成公共契约，之后每次重构都变成破坏性变更。这正是原开发文档「初期不做插件系统，重点做好核心架构」的工程化展开。

---

## 2. 三层扩展模型

系统的可扩展性按成本从低到高分三层。**MVP 只建设 L1/L2，L3 仅预留演进路径不写代码。**

```
L1 配置开关        settings KV + feature flags        —— 不写代码即可改变行为
L2 模块化扩展      新增 modules/* + 注册表 + 事件       —— 写一个目录即可获得完整能力
L3 插件系统        外部包/独立进程 + 版本化 ABI         —— 未来按需立项（§5 触发条件）
```

### L1 · 配置开关（settings 驱动）

- `settings` 表（KV + JSONB）是运行时行为的唯一事实来源：`site.mode`（blog/forum/hybrid）、每页条数、SEO 项等；
- 新功能落地时优先问一句：「这个能不能做成 settings 开关？」能开关的就不写分支部署；
- 写入即失效 Redis 缓存键（约定 `settings:*`），全站秒级生效。

### L2 · 模块化扩展（当前主战场）

**后端**：每个域一个 `modules/<name>/` 自治目录：

```
modules/cms/
├── models/  repositories/  services/   ← 内部实现，外部不可见
├── http/                                 ← 专用动作路由
├── events/                               ← 对外广播的业务事实
├── jobs/                                 ← 异步能力
└── register.go                           ← 唯一对外入口：向各注册表登记
```

模块接入系统能力靠四个**注册表**（都是 M1–M4 要落地的代码）：

| 注册表 | 扩展什么 | 对应机制 |
|---|---|---|
| ResourceSpec | 管理端 CRUD 资源 | adminhub 通用网关（计划 §7.3） |
| Event | 业务事实广播 | Goravel Event：如 `ArticlePublished`，任何新模块可订阅而不改发布方 |
| Queue Job | 异步任务 | 计数落库、AI 占位 Job 等 |
| Schedule | 定时任务 | 浏览量落库、会话清理等 |

**依赖铁律**（计划 §7.2 重申）：模块间只经 Service 接口或事件通信；`adminhub` 被单向注册；出站请求必走 `support/safefetch`。

**管理后台**：nuxtadmin 天生就是这套模式——业务以 `defineModule({ resources, widgets, navGroups })` 声明式注册，框架层（core/framework/ui）冻结不改。加一个后台资源 = 在 `app/modules/<name>/` 写一个 Resource 文件并在组合根登一行。**这就是后台侧的"插件"，且已经存在，无需再发明。**

### L2 的验收标准

> 「新增一个中等复杂度的业务能力（如未来的『友情链接』），是否只需：新建 modules/links + 注册 Spec + 后台加一个 module 目录 + 组合根一行？」

若答案为否、需要改动 core 或既有模块内部，即视为架构回归，PR 必须说明理由。

## 3. 主题设计（前后端功能分离）

### 3.1 总原则：后端无头化（Headless）

- 后端只提供 `/api/v1/**` 数据契约与 `/api/admin/**` 治理契约，**不感知**任何视觉呈现；
- 主题切换不需要后端参与，也就不存在「主题 API」——避免 WordPress 式的主题钩子污染核心；
- 站点模式（site.mode）与主题是两个正交轴：**mode 决定暴露哪些内容板块，theme 决定长什么样**。博客模式 + 任意主题、共存模式 + 任意主题，自由组合。

### 3.2 公共前台主题 = Nuxt Layers（Phase B）

Nuxt 4 的 Layers 机制天然适合做主题包：

```
frontend/
├── app/                    # 宿主应用：只含站点配置（读 /api/v1/site/config）
│   └── nuxt.config.ts      # extends: ['../themes/blog', ...] 按需组合
├── themes/
│   ├── base/               # 基础层：类型、composable、API client、布局骨架
│   │   ├── composables/useSiteConfig.ts useArticles.ts ...
│   │   └── components/PageShell.vue ...
│   └── blog/               # 博客主题层：首页/文章页/标签页的具体模板
│       └── app/pages/ components/
```

规则：

1. **主题层只消费契约，不触碰契约**——所有数据访问走 `themes/base` 里基于 `/api/v1` 的 client，主题间禁止互查内部实现；
2. 模式感知路由在宿主层处理：`site.mode=blog` 时论坛路由不注册（见计划 §5.4 门控语义，前端路由只是同一语义的镜像）；
3. SEO 关键项（meta/canonical/OG/sitemap）属于 base 层基础设施，主题层只填充内容字段。

### 3.3 管理后台主题 = 设计令牌（低优先级）

nuxtadmin 基于 Tailwind v4 + shadcn 风格组件，换肤即调整 CSS 变量令牌（色板/圆角/密度），存于其 ui 偏好 store。属纯装饰需求，排在 MVP 全部里程碑之后，不做也不影响任何功能。

## 4. AI 能力的同构性验证

AI（计划 O8）是检验本扩展模型的自测试剂：它应当完全以 L2 方式接入——

```
modules/ai/register.go:
  Event.Subscribe(ArticlePublished) → Queue.Dispatch(GenerateSummaryJob)
  GenerateSummaryJob → 经 safefetch 调模型 → 回写 articles.ai_summary
  未配置 provider 时：Job 直接 no-op 返回
```

核心链路（文章发布）零改动、零 import。如果未来某个需求无法用 L1/L2 表达，先怀疑需求或抽象，而不是急于引入 L3。

## 5. L3 插件系统：触发条件与形态（预留，不排期）

**触发条件（满足任一再评估）**：

1. 出现第三方开发者在**我们不可控的代码库之外**扩展系统的真实需求；
2. 同一部署需要服务多个租户且租户要求互异的定制逻辑；
3. 单体构建时间/团队规模导致 modules 并行开发冲突显著（通常 >8 人后端团队才成立）。

**届时的推荐形态**（记录现状认知，届时重新评估）：

- Go 侧优先「编译期插件」：独立 Go module + go.mod replace 接入，复用同一套注册表——因为 L2 的注册表接口就是未来的 ABI，这也是现在必须把它们设计干净的原因；
- 进程外插件（gRPC sidecar）仅用于重资源场景（如独立 AI 服务），走既有的 `/api/v1` 与消息边界；
- 前台主题包天然可分发（npm 包），无需额外插件设施。
